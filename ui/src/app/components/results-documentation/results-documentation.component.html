CQL Test Results Viewer Documentation

Query Parameters

The results UI supports query parameters for loading data and deep-linking to filtered views. Loading happens on /results/open; the viewer at /results applies filter and organization parameters once results are loaded.

Supported Parameters

Parameter Description Values Example
url URL to a JSON results file. Accepted on /results/open and /results. Valid HTTP/HTTPS URL ?url=https://api.example.com/results.json
index URL to an index JSON file listing available result files. Handled on /results/open. Valid HTTP/HTTPS URL to index.json ?index=https://api.example.com/index.json
status Initial status filter in the viewer all, pass, fail, skip, error ?status=fail
search Initial search term in the viewer Any text string ?search=arithmetic
groupBy Initial grouping option none, group, status, testsName ?groupBy=group
sortBy Initial sorting field name, group, status, expression, testsName ?sortBy=name
sortOrder Initial sort order asc, desc ?sortOrder=desc

Combined Usage Examples

Open a results file and filter to failed tests:

/results/open?url=https://api.example.com/results.json&status=fail

Load results and search for specific tests:

/results/open?url=https://api.example.com/results.json&search=arithmetic

Load results with both status and search filters:

/results/open?url=https://api.example.com/results.json&status=error&search=division

Load results grouped by test group and sorted by name:

/results/open?url=https://api.example.com/results.json&groupBy=group&sortBy=name&sortOrder=asc

Load failed tests grouped by status and sorted by expression:

/results/open?url=https://api.example.com/results.json&status=fail&groupBy=status&sortBy=expression&sortOrder=desc

Complete example with load and viewer parameters:

/results/open?url=https://api.example.com/results.json&status=error&search=arithmetic&groupBy=group&sortBy=name&sortOrder=asc

Load from index file:

/results/open?index=https://api.example.com/index.json

Load from index with filters (applied after you pick a file):

/results/open?index=https://api.example.com/index.json&status=fail&search=arithmetic
After a file is chosen, the app navigates to /results with url (and any filter parameters) preserved so the same view can be bookmarked or shared.

Index File Support

Loading from Index Files

On /results/open, you can load an index file that lists available result JSON files. This is useful for CI/CD systems or hosts such as cql-tests-results that publish multiple result files behind a single index.

Index File Format

Index files must be valid JSON with a files array of result file names (or relative paths) resolved against the directory that contains the index:

{{ '{' }}
  "files": [
    "results-2024-01-15.json",
    "results-2024-01-16.json",
    "results-2024-01-17.json"
  ]
{{ '}' }}

Using the Index Parameter

When you provide an index parameter on /results/open, the application will:

  1. Load the index file from the specified URL
  2. Display a list of available result files
  3. Let you select a file, which loads it and navigates to /results

Index with Filter Parameters

You can combine the index parameter with filter parameters. When a user selects a file from the index, those filters are carried into the viewer URL and applied to the loaded results.

Programmatic Integration & Deep Linking

Deep Linking for CI/CD

Integrate the viewer into your continuous integration pipeline by generating direct links to filtered results. On the viewer page, the application updates the URL when users change controls, which makes it easy to share a specific view.

Real-time URL Synchronization

On /results, the application updates query parameters when users interact with controls:

  • Status Filter - Updates status parameter (omitted when set to all)
  • Search Term - Updates search parameter
  • Grouping - Updates groupBy parameter (omitted when none)
  • Sorting - Updates sortBy and sortOrder when they differ from the defaults (name / asc)
  • Data Source - Preserves url when results were loaded from a remote file
Pro Tip: Bookmark URLs with specific filters for quick access to commonly used views, or share them in team communications for collaborative analysis. A complete URL that includes url (or that was opened via /results/open) will reload the same data source and view.

Schema Validation Details

When Validation Runs

If Validate schema is enabled in settings, opening a results file validates against the CQL Test Results schema before navigating to the viewer. Validation prefers the runner API (POST /validate/results endpoint and falls back to client-side AJV validation if the runner is unavailable.

Validation Rules

Required top-level fields:

Required Fields Validation

  • cqlengine - Must contain all required fields:
    • apiUrl - Must be a non-empty string
    • description - Must be a non-empty string
    • cqlVersion - Must be a non-empty string
    • cqlTranslator - Must be a non-empty string
    • cqlTranslatorVersion - Must be a non-empty string
    • cqlEngine - Must be a non-empty string
    • cqlEngineVersion - Must be a non-empty string
  • testResultsSummary - Must contain passCount, skipCount, failCount, and errorCount as integers
  • testsRunDateTime - Must be a valid ISO 8601 date-time string
  • results - Must be an array of test result objects
  • testsRunDescription - Optional string describing the run

Test Result Object Validation

  • testsName, groupName, testName, expression - Required strings
  • testStatus - When present, must be one of: pass, fail, skip, error
  • actual / expected - Optional strings
  • error - Optional object; when present, message is required
  • invalid - Must be one of: true, false, semantic (if present)
  • responseStatus - Optional integer HTTP status from the evaluation call
  • capabilities - Optional array of capability objects (if present):
    • code - Required string
    • value - Optional boolean, string, number, object, or array
    • system - Optional string
    • display - Optional string
    • version - Optional string

Validation Error Handling

When schema validation is enabled and validation fails, the application:

  • Displays detailed error messages for each validation failure
  • Does not navigate to the viewer until validation succeeds
  • Leaves the loaded payload on the open page so you can inspect the reported issues

To open a non-conforming file anyway, disable schema validation in settings and reload the file. Filtering and organization still work on whatever structure the viewer can read.

Advanced Filtering & Organization

Search Capabilities

The search functionality performs case-insensitive substring matching across:

  • Test Name (testName)
  • Group Name (groupName)
  • Test Suite Name (testsName)
  • CQL Expression (expression)

Status Filter Combinations

Status filters work in combination with search terms:

  • Search for "arithmetic" + filter by "fail" = Failed arithmetic tests only
  • Search for "division" + filter by "error" = Division tests with errors only
  • Search for "string" + filter by "pass" = Successful string operation tests only

Grouping & Sorting Features

Organization tools for large result sets:

Grouping Options

  • None - Display all results in a single list
  • Group Name - Group tests by groupName
  • Status - Group tests by pass/fail/skip/error status
  • Tests Name - Group tests by suite name (testsName)

Sorting Options

  • Test Name - Alphabetical sorting by test name
  • Group Name - Alphabetical sorting by group name
  • Status - Lexicographic sort by status string
  • Expression - Alphabetical sorting by CQL expression
  • Tests Name - Alphabetical sorting by test suite name

Sort Order

  • Ascending - A-Z / 0-9 for the selected field
  • Descending - Z-A / 9-0 for the selected field

URL Encoding for Special Characters

When using query parameters with special characters, ensure proper URL encoding:

  • Spaces: %20 or +
  • Special characters: Use percent encoding
  • Unicode characters: UTF-8 encoding

Example: ?search=arithmetic%20operations&status=fail&groupBy=group
