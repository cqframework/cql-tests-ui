CQL Test Runner Documentation

CQL Test Runner Overview

The CQL Test Runner UI submits jobs to a CQL Tests Runner API service, which executes the community cql-tests suites against a FHIR server that exposes CQL evaluation operations.

What is the CQL Test Runner?

The runner is an HTTP client to a FHIR server, not a built-in CQL engine. Engine and translator names you configure are recorded as metadata on the results. From this UI you can:

  • Execute CQL Tests - Run the shared language test suites against a configured FHIR server
  • Configure Test Parameters - Set FHIR server settings, CQL version metadata, and skip/only lists
  • Manage Test Jobs - Create, monitor, and track long-running test executions
  • Analyze Results - Download JSON results and open them in the results viewer
  • Skip or Whitelist Tests - Exclude specific tests or restrict a run to a named set

Key Features

FHIR Server Integration

Call a FHIR R4 server using $cql (system-level) or $evaluate (Library/$evaluate). Expression tests use $cql by default; library-style tests require $evaluate.

Flexible Configuration

Configure CQL file version, CQL language version filtering, engine/translator metadata, and debug options through the form or JSON editor.

Asynchronous Execution

Run tests as background jobs with status polling and elapsed-time tracking.

Results Management

Download test results in JSON format and view them directly in the results viewer.

Workflow Overview

  1. Configure Settings - Set the runner API URL under Settings, then configure the FHIR server and test parameters on this page
  2. Create Test Job - Submit a test execution request to the runner service
  3. Monitor Progress - Track job status while the service runs the suites
  4. Download Results - Retrieve test results when the job completes
  5. Analyze Results - Use the results viewer to examine pass/fail/skip/error outcomes
Note: A reachable CQL Tests Runner API must be configured (Settings → Runner) before you can create jobs. The suites under test generally evaluate expressions only and do not retrieve patient data from the FHIR server.

Configuration Modes

The runner supports two configuration modes:

  • Form Editor - Visual form-based configuration with individual input fields
  • JSON Editor - Direct JSON configuration editing for advanced users (includes path fields and full schema)
Tip: Use the JSON editor for complex configurations or when copying settings between environments. The form editor is recommended for most users. Leave QuickTest enabled for a fast connectivity check, then disable it for a full suite run.

Test Execution Process

Understanding how CQL tests are executed and what happens during the process.

Execution Flow

  1. Job Creation - Submit configuration to the runner service
  2. Validation - Verify configuration against the runner schema
  3. Test Preparation - Load suites from cql-tests and apply QuickTest / OnlyList / SkipList filters
  4. Test Execution - Evaluate each remaining test via $cql or $evaluate on the FHIR server
  5. Result Collection - Compare actual vs expected values and compile a summary
  6. Job Completion - Mark the job complete (or failed) and make results available

Quick Test vs Full Run

Quick Test (QuickTest: true)

Smoke-test mode used by default in the UI:

  • Loads only the first suite in the test set
  • Within that suite, loads only the first group
  • Useful for verifying connectivity and configuration

Full Run (QuickTest: false)

Runs every suite and group loaded by the runner:

  • All expression (and applicable library) tests
  • Still respects SkipList, OnlyList, and CQL version gating
  • Can take a long time depending on suite size and server latency

Test Results Structure

Each completed job produces a JSON document matching the CQL Test Results schema, including:

  • Engine Metadata - cqlengine block with API URL, versions, and labels
  • Summary Counts - pass, fail, skip, and error totals
  • Per-Test Status - pass, fail, skip, or error
  • Actual / Expected - Serialized values used for comparison (when present)
  • Error Details - Message (and optional name/stack) for failures and errors
  • HTTP Response Status - Optional status code from the FHIR operation call

Individual results do not include per-test execution duration.

Skip List and Only List

Both lists identify tests by the exact triple testsName + groupName + testName:

  • SkipList - Mark matching tests as skipped and record a reason
  • OnlyList - When non-empty, skip every test not listed
  • Precedence - A test present in both lists is skipped
  • No wildcards - Omitting or leaving a field blank does not skip an entire suite or group; list each test explicitly

Performance Considerations

Important: Test execution time varies based on:
  • Whether QuickTest is enabled
  • Number of tests after SkipList / OnlyList filtering
  • Complexity of CQL expressions
  • FHIR server response time and load
  • Network latency

Job Management

The CQL Test Runner UI uses asynchronous job processing for long-running test executions.

Job Lifecycle

Pending

Job created and queued for execution

Running

Tests are actively being executed

Completed

Job finished without a runner failure (individual tests may still fail or error)

Failed

Job encountered an error before producing usable results

Job Monitoring

Once a job is created, the UI monitors progress automatically:

  • Status Updates - Polls the runner API every 2 seconds while status is pending or running
  • Progress Indicators - Status badges and elapsed-time display
  • Error Reporting - Toast notification and error field when a job fails
  • Completion Alerts - Toast notification when a job completes or fails

Job Information

Each job provides detailed information:

Field Description
jobId Unique identifier for tracking the job
status Current execution status (pending, running, completed, failed)
createdAt Timestamp when the job was created
completedAt Timestamp when the job finished (if completed or failed)
message Human-readable status message
error Error details (if the job failed)

Job Actions

Once a job completes successfully, you can:

  • Download Results - Get the complete test results as JSON
  • View Results - Open results directly in the results viewer
  • Reset Configuration - Clear the form and start over

Best Practices

Tips for Job Management:
  • Confirm the runner API health check succeeds before creating a job
  • Start with QuickTest enabled, then disable it for a full suite run
  • Download or view results soon after completion
  • Keep job IDs for reference and troubleshooting
  • Use descriptive SkipList reasons so skipped tests are explainable later
